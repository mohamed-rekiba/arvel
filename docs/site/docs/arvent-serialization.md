# Serialization

Every Arvel model can convert itself to a `dict` or a JSON string. The default serializer respects column casts, hides private attributes, and traverses loaded relations.

## `to_dict()` and `to_json()`

```python
user = await User.find_or_fail(1)

user.to_dict()
# → {"id": 1, "name": "Alice", "email": "a@b.com", "created_at": "2026-05-19T00:00:00+00:00"}

user.to_json()
# → '{"id":1,"name":"Alice","email":"a@b.com","created_at":"2026-05-19T00:00:00+00:00"}'

user.to_json(indent=2)
# Pretty-prints for logs and fixtures.
```

`to_json()` is the JSON twin of `to_dict()`: identical visibility rules, but serialised through Pydantic's core encoder so `datetime`, `Decimal`, `UUID`, and `bytes` round-trip the same way they do in framework HTTP responses.

### Value-object columns (custom `PydanticType`)

Columns backed by a Pydantic value object — anything declared with `mapped_column(PydanticType(MyModel), ...)` — serialize as the nested object shape, not as a flattened scalar. `to_dict()` returns the model dump as a `dict`, and `to_json()` produces the matching JSON payload. If your API contract needs a different shape (a flat string, a custom field set, etc.), expose the field via a [Pydantic schema](arvent.md#generating-a-model) — that's exactly what the boundary schemas are for. The serialization layer never silently flattens; that's a [JSON Resource](arvent-resources.md) concern.

## Hiding fields

Use the dunder attributes — they're class-level lists picked up by `to_dict()` and `to_json()`.

```python
from typing import ClassVar

from arvel.database import Model, Timestamps, id_, string


class User(Model, Timestamps):
    __tablename__ = "users"

    __hidden__: ClassVar[list[str]] = ["password", "remember_token"]

    id: Mapped[int] = id_()
    email: Mapped[str] = string(180, unique=True)
    password: Mapped[str] = string(255)
```

`__hidden__` is a deny-list — listed attributes never appear in serialised output. The mirror image is `__visible__`, an allow-list of attributes that ARE included. Define one or the other, not both — `__visible__` wins when both are set.

You can also pass a per-call hidden list:

```python
user.to_dict(hidden=["email"])
# Hides "email" for this call only; class-level __hidden__ still applies.
```

## Loaded relations

If you eager-load a relation before fetching, `to_dict()` includes it automatically:

```python
user = await User.with_("posts").find_or_fail(1)

user.to_dict()
# → {"id": 1, ..., "posts": [{"id": 10, "title": "..."}]}
```

Relations that are NOT loaded are omitted — no surprise N+1. Reach for `to_pydantic(schema)` (next section) when you want a relation to be required.

## `to_pydantic(schema)`

When the boundary shape is fixed and you'd rather get a Pydantic error than a forgiving dict, project the model through a schema generated by [`make:schema`](console.md#scaffolding-make):

```python
from app.schemas.user_schema import UserRead

user = await User.find_or_fail(1)
payload: UserRead = user.to_pydantic(UserRead)
```

`make:schema User` writes `UserRead`, `UserCreate`, `UserUpdate` from the column metadata; server-managed columns (auto-increment PKs, `Timestamps`, `SoftDeletes`) are excluded from `Create` / `Update`. The schemas are meant to be edited — `make:schema --force` overwrites the file when the model shape changes.

## Custom serialization

For richer control — shape changes, computed fields, request-aware logic — use a [JSON Resource](arvent-resources.md) instead of overriding `to_dict()`. Resources keep the per-request transformation out of the model where it doesn't belong.

## Collections

Model collections serialise through `to_json()` element-wise:

```python
users = await User.limit(5).get()

users.to_json()
# → '[{...}, {...}, ...]'

users.to_array()
# → [User(...), User(...), ...]  — plain list, untouched objects
```

Each element's `to_dict()` is invoked when the collection serialises to JSON, so per-model `__hidden__` / `__visible__` rules are honoured.
